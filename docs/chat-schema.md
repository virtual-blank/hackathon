# Чаты: принятое решение

- **Статус:** согласовано (Данил, Макс)
- **Суть:** одна таблица `messages`, отдельной сущности «чат» нет

---

## Решение

Изначально не хватало признака прочтения в таблице `messages`. Добавляем два поля и индексы.

Несколько таблиц (`chats` + `chat_members`) решили **не вводить**: они нужны только для групповых чатов и настроек конкретного диалога (мьют, архив, закрепление). У нас простой личный чат 1-на-1, поэтому достаточно одной таблицы.

Функционал чата:
- порядок сообщений — по `id`, внутри которого UUIDv7 хранит время создания;
- прочитано / не прочитано — поле `is_read`, плюс `read_at` с моментом прочтения;
- только текст, до 2000 символов, без медиа и голосовых.

---

## Схема таблицы `messages`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | UUIDv7 | идентификатор; внутри время, поэтому сортировка по `id` равна сортировке по времени |
| `sender_id` | UUID | отправитель |
| `receiver_id` | UUID | получатель |
| `content` | текст | до 2000 символов, проверяет Pydantic |
| `is_read` | bool | прочитано получателем |
| `read_at` | время, NULL | когда прочитано |
| `created_at`, `updated_at` | время | стандартные |

Индексы:
- `ix_messages_dialog (sender_id, receiver_id, id)` — история в направлении «я → собеседник» (уже был);
- `ix_messages_dialog_reverse (receiver_id, sender_id, id)` — история в обратном направлении, потому что переписка двусторонняя;
- `ix_messages_receiver_unread (receiver_id, is_read)` — подсчёт непрочитанных.

---

## Как считаются основные вещи

Непрочитанные от собеседника:

```sql
SELECT count(*) FROM messages
WHERE receiver_id = :me AND sender_id = :peer AND is_read = false;
```

Отметка прочтения (всё до указанного сообщения включительно):

```sql
UPDATE messages
SET is_read = true, read_at = now()
WHERE receiver_id = :me AND sender_id = :peer
  AND id <= :last_read_message_id AND is_read = false;
```

Список диалогов: последнее сообщение по каждому собеседнику через оконную функцию `row_number()`, плюс количество непрочитанных отдельным запросом — итого два запроса, без обхода диалогов по одному.

## Правила доступа

- Переписка доступна только друзьям — статус `accepted` в таблице `user_relations`.
- Если кто-то кого-то заблокировал (`blocked`) — ответ `403`.
- Писать самому себе нельзя.

---

## HTTP-ручки

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/social/chats` | список диалогов: собеседник, последнее сообщение, непрочитанные |
| GET | `/api/social/chats/{peer_id}/messages?limit&before_id` | история диалога, свежие первыми |
| POST | `/api/social/messages` | отправить сообщение: `{peer_id, content}` |
| POST | `/api/social/chats/{peer_id}/read` | отметить прочитанным до `last_read_message_id` |
| POST | `/api/social/ws-ticket` | одноразовый пропуск для подключения к вебсокету |

---

## Чего это решение не даёт

- **Групповые чаты** — потребуют таблиц `chats` и участников.
- **Настройки диалога** (мьют, архив, закрепление) — для них тоже нужна сущность чата.
- Всё остальное покрыто: порядок есть, прочтение есть, момент прочтения есть.
